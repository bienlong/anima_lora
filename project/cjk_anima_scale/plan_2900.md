## 3a. Run C on Colab — notes (no Colab-side code in the line)

The user runs C off the local GPU through the `colab` CLI (uv tool,
`google-colab-cli`), over `colab ssh`. What the line's code assumes, and
what that means on a Colab VM:

- **Session.** `colab new --gpu <T4|L4|G4|H100|A100> -s <name>` (the CLI's
  list has no L40; L4 is 24 GB), then `colab ssh -s <name>` (a shell in
  `/content`). For rsync / scp, `~/.ssh/config` takes
  `ProxyCommand colab ssh --proxy-mode -s <name>`. `colab usage` shows the
  compute-unit balance.
- **Install: a Colab branch is needed.** The Colab VM runs CUDA 12.8 on
  driver 580 with torch `2.11.0+cu128` (user, 2026-09-27). The repo's lock
  is built for this box:
  `pyproject.toml` routes `torch>=2.12,<2.13` / `torchvision` through the
  `pytorch-cu132` index (local: `2.12.0+cu132`, driver 610), and it pins
  flash-attn to the `cu132torch2.12-cp313` prebuilt wheel. A plain
  `uv sync` on the VM would pull cu132 builds the 580 driver may not run.
  So cut a branch (e.g. `colab-cu128`) that changes only the install
  surface:
  - the torch / torchvision index → `pytorch-cu128`, and the pin →
    `torch==2.11.0` (the VM's known-good build) with its matching
    torchvision. This steps below the repo's `>=2.12` floor, so check that
    the code the line runs has no 2.12-only API (torch.compile /
    dynamic-shape paths first) before trusting a run;
  - flash-attn → a `cu128torch2.11-cp313` wheel, or dropped if none exists
    (check whether the line's DiT path needs it);
  - a fresh `uv lock` on the branch; `requires-python` stays 3.13, since uv
    installs its own Python on the VM.
  Smoke on the VM before a run: `torch.cuda.is_available()`, one
  `scale.py <run> train` step with `torch.compile` (Triton has to build for
  that GPU), and the pack's sha in the load log. The branch never merges
  into main; it carries only the install change.
- **No daemon there.** The daemon rule is for agent-launched local GPU
  work. On the VM, run `scale.py <run> data` and `scale.py <run> train`
  directly, with `ANIMA_VOCAB_PACK=models/vocab_packs/anima_cjk_vocab_pack`
  set (sha `7b9fce0bb57b…`, 272 MB).
- **What goes over.** The repo at the same commit + `uv sync`; the models
  `library.env.default_checkpoints()` resolves (DiT, `qwen_3_06b_base`,
  `QwenImage_VAE_2d`) and the pack; the seed rows
  `output/cjk_anima_scale/rows_step1_0921_merged/trained.pt` (8.9 MB, all
  `train` needs of that dir); `assets/fonts/` (80 MB, gitignored); the scene
  pools the recipes draw (`scenes_s1`, `scenes_s1w` for C-k; C-p also
  `scenes_sl1w`, `scenes_ja_comic`; 130–180 MB each). C-p's piece tiers also
  read `$MANGA109S/derived/dialogue_2_10.tsv` through `.env`; that corpus
  stays out of the repo, so it goes to the VM by hand and stays there.
- **Path trap.** `train.jsonl` records each item's absolute `file`
  (`/home/sorryhyun/anima/anima_lora/output/…`), and the trainer's latent
  cache reads it. Build the data on the VM, or put the checkout at the same
  absolute path (a symlink is enough). Uploading a local data dir is also
  heavy: ≈ 43 k items for C-k (300f's 10 k-item stage dir was 2.2 GB).
- **No resume.** `train` writes `trained_partial.pt` every 5 000 steps but
  cannot resume from it, so a VM that drops mid-run loses the run. C-k is
  ≈ 7 h at the local 2.1–2.35 it/s, and the Colab it/s is unmeasured.
  Check the session limit against the run length before launching.
- **What comes back.** `<run>/trained.pt`, `train_record.json`,
  `train_log.json`, and `<run>/data/{vocabs.json,build.json,eval.json}`.
  `merge` reads `vocabs.json` to find the run's own idx, and `eval` needs
  `eval.json`. **Eval runs locally through the daemon**, because the floor is
  one local read cache (`rows_step1_0921_merged/`); a VM-side eval would
  render a second floor.
- The C-k budget (150 vs 270) is still open; it is `budget.RULES`' cold-single
  row, so settle it before the VM launch.

(≈ 3 270 rows). Eval it once on `en` / あ い / `sent` / `word` / piece, then

## 5. Code before the first launch — done 2026-09-27

Built as below; line tests 80 / 80 (`tests/test_line.py`: `test_budget_rule`,
`test_plan_groups_take_the_budget`, `test_ruler_sample`, `test_single_ruler`,
`test_merge_rows`, the front-door `merge` parse). What differs from the
draft:
- 1 → `cjk_scale/budget.py`: rows with provenance, like `windows.py`, today
  one row (cold single 150). A factor scales both `train.STEPS_PER_VOCAB` and
  `builder.ITEMS_PER_VOCAB`. **A run's vocabs must share one factor**: the
  builder and batcher draw uniformly, so a mixed run would spread its budget
  evenly. `run_factor` refuses it; split the run and merge. Steps are
  per-row × the run's idx, as before. Warm singles are unchanged
  (factor 1), so the A0 jobs ran on identical code paths.
- 2 → `eval.RULER_N = 24`, and `ruler_sample` draws round-robin over
  glyph-count strata (so 8 per count at 3 / 4 / 5). The piece ruler keeps
  the `read` strings' pieces first. Its old sample (the `word` group's 8) is
  gone, so an old run re-evaluated renders new floor keys. **A's read is 24
  of the 305** (one stratum), not "the 58 in full plus 24 of the 247" of § 1.
  A0's 12 floor keys sit in `native_densea0/`, not `native_single/`.
- 3 → `cjk_scale/merge.py`: the first run is the base. Each other run's idx
  (its `vocabs.json` through the tokenizer, `train.vocab_idx`) overwrite the
  base rows, and a vocab cold in its run is appended (ids sorted). Refused:
  overlap, different seeds, a `line` mode, a stopped-early file. CPU, no
  `--submit`. **Not built:** evaluating the merged dir (`eval` wants a run
  toml + a data dir with `eval.json` / `vocabs.json`).
- 4 → the files, cut by a one-off script (not kept). The headers record each
  cut. Dense: ink ≥ 10.98 reproduces § 1's 58 + 247, because 旅 and 落 read
  703 px with `src/eval/cf_sense.py::_glyph_ink`, 704 in the draft's measure.
  C: § 3's counts. Run tomls: A / C-k read the single ruler only; B / C-p
  read `run0925_300f`'s sent strings (cached floor).

The draft:

1. **Budget rule** (`train.py` + `builder.py`): steps and items per vocab by
   kind × glyph count × warm/cold. Cold single: 150. 3+-glyph piece: B0's
   number. Everything else: 90. Items scale with the steps. A run's steps are
   the sum over its vocabs. Provenance: `stage_i` § 5, and B0's report. This
   is a rule, not a run key (plan.md § 2).
2. **`single` native ruler** (`eval.py`, mirroring `piece`): the run's single
   vocabs rendered alone, `en`, with floor keys through
   `ensure_native_floor`, and per-glyph official / contained in `reads.json`.
   Its sample size and the piece ruler's cap (8 today) become one rule: all
   of a run's vocabs up to 24, then a seeded sample stratified by glyph count.
3. **`merge` verb** (`scale.py <out> merge <run>…`): disjoint rows from the
   same seed, with the `row_scale` rescale. It refuses overlapping idx.
4. Vocab files: `ja_dense_k_0927_305.txt`, `ja_long_p_0927_521.txt`,
   `ja_cold_1901_2900_{k,p}.txt`. They use `ja_cold_0001_1900.txt`'s TSV
   columns, and each header records its cut. Plus
   `configs/runs/run0927_{dense_k,long_p,cold_k,cold_p}.toml`.
